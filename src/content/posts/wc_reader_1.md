微信读书是一套自研的排版引擎，它并不是使用浏览器内核直接渲染网页，而是先进行“大清洗”，清洗掉html中它不信任的属性，然后转换成一套其私有格式，再通过自己的排版引擎进行渲染。因此它天生对EPUB的支持就极其有限，所以非常影响epub的阅读体验，这带来了两点问题。

- 对跳转注释和epub3的标准弹出注释都支持的不好，无法正常使用注释
- 对于一些制作不精良的电子书，如果每一章没有使用单独的`xhtml`文件[^xhtml]，那么就只能通过`toc.ncx`配合`#id`锚点来实现导航栏的章节跳转，但软件内的页眉的显示的章节始终指向**文件开头第一个目录项名称**。

因此分为两个部分，注释部分和目录部分。

## 背景
为了所谓的无纸化学习吧~~懒得买书~~整了个华为平板，毕竟都说华子书写体验好，这个平板除了记笔记和写题以外最大的作用已经成为Kindle了，在柔光屏上看小说岂不快哉！但很快遇到了第一个大问题，怎么做到阅读进度的同步呢？毕竟无法做到随时随地带一个平板出行吧。

在经过一番搜索后，发现只有微信读书能够满足这个需求了，在安卓和鸿蒙都有，并且功能也算完整，同时支持进度同步。当然也有其他软件支持，比如[Reeden](https://reeden.app/), [Legado](https://github.com/LegadoTeam/legado)等，但是第一个软件多端同步得花98，第二个鸿蒙侧载+WebDAV，有点折腾，所以最后还是选择了微信读书。~~好像为了微信读书研究epub格式也很折腾？？~~

如果到后面真的养成了读书的习惯可能就直接花98去买一个Reeden，或者直接买一个真正的Kindle了？不过目前的微信读书应该是可用的，前提是不加载一些非常复杂排版的书籍。

## 注释部分

### 3种常见注释写法

#### 1. EPUB2的传统写法：双向超链接注释跳转

```html
<!-- 1. 正文里的引用点（id="ref1"，跳往 #annot1） -->
<p>……听着电车里的BGM<span class="super"><a id="ref1" href="#annot1">[1]</a></span>……</p>

<!-- 2. 章末的注释区（id="annot1"，跳回 #ref1） -->
<p class="fnote"><a id="annot1" href="#ref1">[1]</a> 注：背景音乐。</p>
```
表现为正文里出现一个带链接的数字上标`[1]`，点击后会跳转到本章的注释区；再点击注释区的相同数字即可返回原阅读进度。（补充：现代阅读器如 KOReader、Apple 图书也会通过算法自动识别这种双向链接，直接帮你转成弹窗）

在微信读书中`<a href>`跳转链接虽然保留，但是*底层屏蔽了所有`<a href>`的点击跳转事件*，变成了死链接。但`<a href>`仍然是按照超链接渲染的，让读者误以为可以点击。并且部分书籍会使用独立的css文件来规范注释格式，但如果使用内联`style`属性却无法渲染，原因点击此处跳转[下文](#配套css样式)。

#### 2. EPUB3标准写法：语义化弹窗注释
```html
<!-- 必须先在 html 根标签声明 epub 命名空间 -->
<html xmlns="http://www.w3.org/1999/xhtml" xmlns:epub="http://www.idpf.org/2007/ops">
<!-- 1. 正文里的引用点 -->
<p>……听着电车里的BGM<a epub:type="noteref" href="#fn1">[1]</a>……</p>
<!-- 2. 注释本体（标准阅读器平时会自动隐藏 <aside>，点击时才弹出） -->
<aside id="fn1" epub:type="footnote">
  <p>[1] 注：背景音乐。</p>
</aside>
```
表现为点击`[1]`，页面不跳转，直接在当前位置弹出一个半透明气泡或者底部卡片显示注释；在正文排版中，注释会被隐藏。这也是目前阅读器的推荐写法。

> [!WARNING]
> 在微信读书中，不弹窗，且**内容泄露**。微信读书既不识别`epub:type="noteref"`，也不隐藏`<aside>`，而是直接把`<aside>`当成普通正文段落`<p>`印在页面上。

#### 3. 国内排版独有标准：多看弹出注释+双兼容写法
```html
<!-- 1. 正文引用：同时写上 epub:type="noteref" 和 class="duokan-footnote" -->
<p>……BGM<a class="duokan-footnote" epub:type="noteref" href="#fn1" id="fnref1"><img src="../Images/note.png"/></a>……</p>

<!-- 2. 注释本体：同时用 <aside epub:type="footnote"> 和 class="duokan-footnote-item" -->
<aside class="duokan-footnote-item" epub:type="footnote" id="fn1">
  <ol class="duokan-footnote-content">
    <li><a href="#fnref1">注：背景音乐。</a></li>
  </ol>
</aside>
```
正文里显示一个“注”字小图标或上标，点击后弹出气泡框，且支持在弹窗里显示多段文字、加粗、甚至多看特有的样式。 

多看阅读团队为了解决EPUB2没有弹窗注释的问题，自己约定了一套class类名规范（引用加`class="duokan-footnote"`，注释区用 `<ol class="duokan-footnote-content">`）。因为当年国内精排电子书圈子全用多看，后来掌阅、静读天下等阅读器全都主动兼容了这套类名。

这种写法在电子书制作圈被称为全平台通吃写法——在Apple图书里走`epub:type`，在多看/静读天下里走`duokan-footnote`，在老阅读器里还能退化成`<a href>`双向跳转。***唯独到了微信读书里全军覆没***。

### 微信读书私有写法

微信读书只认自己从QQ阅读继承来的一套私有图片属性写法。

#### HTML结构
微信读书没有链接、没有独立注释区，并且把注释图标和注释内容全部放到了一个`<img>`标签内

```html
<p>……听着电车里的BGM<img alt="[1] 注：背景音乐。" class="qqreader-footnote" src="../Images/note.png"/>……</p>
```
他的三个属性缺一不可
1. `class="qqreader-footnote"`：触发开关。微信读书扫描带这个class的`<img>`时，会把它当成可点击的弹窗按钮，而不是普通插图。
2. `alt="注释内容"`：数据载体，用来存放注释原文
3. `src="../Images/note.png"`：按钮长相。必须放一张写着“注”字的PNG小图标放到EPUB包里面，同时在`content.opf`里面注册，否则页面内没有东西可以点击。

#### 配套CSS样式
如果不写CSS，那张 $64 \times 64$ 像素的`note.png`会在正文里撑得很大。
> [!IMPORTANT]
> 微信读书格式清洗时会清理掉所有的内联`style="..."`属性，导致样式格式失效。因此所有样式必须写入独立的css文件中。

所以必须要在css文件中规范图片显示，如下：
```css
img.qqreader-footnote {
    width: 1em;              /* 宽度缩放到跟当前正文字号一样大 */
    height: 1em;             /* 高度缩放到跟当前正文字号一样大 */
    vertical-align: super;   /* 像上标 [1] 一样稍微往右上角抬起 */
    margin-left: 0.1em;      /* 左右留一点点呼吸间距 */
    margin-right: 0.1em;
}
```

> [!NOTE]
> 在常用的格式中，正文只有引用标记，注释文字在章末。但微信读书特有格式中，注释文字是合并在正文内的。那么读者在章末还会看到重复一遍的注释，因此在处理书籍时，应删去文件末的`<aside>`或者`<p class='fnote'>`标签。

## 目录部分
### 如何加载整本书
`content.opf`规范阅读器按照怎样的顺序加载`xhtml`文件。
```xml
<!-- content.opf：只认识物理文件 -->
<spine toc="ncx">
  <itemref idref="part0004.xhtml"/> <!-- 书内目录页 -->
  <itemref idref="part0005.xhtml"/> <!-- 《你的名字。》全部10章都在这一个文件里 -->
</spine>
```
### 如何加载目录
`toc.ncx`(EPUB2)或`nav.xhtml`(EPUB3) 这个文件专门负责给侧边栏目录提供树状标题，用`src`指向具体文件，同时支持`#id`锚点指向单文件的具体一行标签。*记住这个锚点，后面要考。*
```xml
<!-- toc.ncx：逻辑目录，可以指向文件开头，也可以指向文件中间的 #id -->
<navPoint id="np_5"><navLabel><text>第一章 梦</text></navLabel>
  <content src="Text/part0005.xhtml"/>                 <!-- 不带 #，指向文件开头 -->
</navPoint>
<navPoint id="np_6"><navLabel><text>第二章 线索</text></navLabel>
  <content src="Text/part0005.xhtml#sigil_toc_id_1"/> <!-- 带 #，指向文件内部第2个 <h1> -->
</navPoint>
<navPoint id="np_7"><navLabel><text>第三章 日常</text></navLabel>
  <content src="Text/part0005.xhtml#sigil_toc_id_2"/> <!-- 带 #，指向文件内部第3个 <h1> -->
</navPoint>
```

因为这两层是分开处理的。所以会在处理物理文件和逻辑章节时会出现三种情况。
- 1对1：这也是epub最支持的方案。一个物理文件对应一个逻辑章节。
- 多对1：某一个逻辑章节可能有多个文件，一般取第一个文件作为`src`放入`toc.ncx`。
- 1对多：一个文件里放入多个逻辑章节，通过`#id`锚点进行区分章节。

### 页码计算
微信读书和普通阅读器都可以正常根据页面渲染的字数算出整本书的页码数量。

但是二者在构建目录时存在一定差异：
- 普通阅读器：将全书分页完毕后，计算出每个章节所在的页数，并写回目录。所以侧边目录每个章节都会有页数。
- 微信读书：凡是直接对应`xhtml`文件的章节，能够正确计算出页码；如果目录的某一章节是使用锚点，即`#id`，那么在侧边目录并不会显示章节对应的页数。目录页码只绑定了*文件级别*的章节。

### 渲染页面与页眉
#### 页面
- 普通阅读器：识别到一个新文件或者在同一个`xhtml`文件里遇到了`<div style="page-break-after:always"></div>`等分页属性，引擎会立刻截断当前页面，新开一个页面。
- 微信读书：处理`xhtml`文件时与普通阅读器一致。但是由于预处理的清洗，内联的`style`属性全部被清理掉，所以无法正常新建页面。并且由于排版引擎本身不支持css的`page-break-after`属性，即使写入独立的css文件也是无效的。在微信读书里能够另起一页的唯一办法就是新建一个`xhtml`文件。

#### 页眉
- 普通阅读器：会把`toc.ncx`里的所有目录项（包含`#id`锚点）在书中的位置排列完毕。每次翻页渲染页眉时，阅读器都会查找当前页面所在的章节区间，渲染出正确的章节。
- 微信读书：只认准`xhtml`文件，所以在渲染页眉时只会拿第一个指向当前`xhtml`文件的目录项作为这个章节的标题。这也就回答了为什么微信阅读对于多章在同一个文件的页眉渲染会出问题。它只会永远渲染这个文件的第一章。

#### 按照文件逻辑的原因
无法保证真实性，AI给出这个原因的时候没有贴出source。觉得挺有道理，所以也写一下吧。

微信读书最早是为了自营线上书城设计的，书城为了分章节付费，所以是按照章节下发文件，那么当然一个文件就对应着一个章节。后来在支持从外部导入EPUB时，仍然沿用了这个逻辑，导致页眉以及分页的错误。

## 小结
贯彻了腾讯系软件一如既往 ***“小而美”*** 的特点。好好的阅读软件偏要搞什么自研引擎，导致对官方的EPUB格式支持稀烂。哪怕随便稍微改改呢，都不至于成这样吧。不过也算是在目前场景下的解决方案了，都是读一些小说，不是排版很复杂的书籍，改文件和注释就已经足够日常使用了。

借助折腾这个事情也算是搞明白一点标记语言的基础知识和epub小说的基本格式，挺有意思的。不得不感慨：*整个世界是一个巨大的浏览器。*

[^xhtml]: 将多个章节合并在同一个 xhtml 文件中、仅靠 #id 锚点区分章节，在 EPUB 标准语法上其实是合法的。
